# Relay v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the relay service and relay mode for Meeting Mirror per the approved v1 design.

**Architecture:** A standalone relay service (rooms live only while a moderator is connected; one moderator per room; browsers connect via SSE at `/s/<name>?key=…`). The extension gains a `RelayClient` that dials out over WebSocket and implements the existing `Transport` interface, plus room-name commands with the room stored in the pi session via `appendEntry`.

**Tech Stack:** TypeScript, `node:http` + `ws` (WebSocket) for the relay, vitest, jsdom for page tests, container build with podman, OpenShift Deployment/Service/Route.

**Spec:** `docs/superpowers/specs/2026-11-04-relay-v1-design.md` (approved)

## Global Constraints

- The relay stores nothing beyond live connections: no transcript, no votes, no rooms between moderator connections.
- One moderator per room; second share of a connected room fails "room busy"; the room frees the instant the moderator disconnects (no grace period).
- The room key is the only credential; every browser request and the presenter connection must present it.
- Session id (per pi run) rides every snapshot; browsers re-ask for names when it changes, not on reconnect.
- Browsers get an SSE heartbeat comment every 25 s; the presenter WebSocket uses ping/pong with a ~30 s timeout.
- Local mode (`MEETING_MIRROR_RELAY` unset) keeps today's behavior; `/mirror share <name|link>` in local mode prints the "needs relay mode" message.
- Room names: `/^[a-z0-9][a-z0-9-]{2,29}$/`; random fallback name: 8 chars Crockford base32 (`0-9a-hjkmnp-tv-z`).
- Votes stay hidden until `/reveal`; the vote update carries voter names (ticks), never choices.
- All production code behind failing tests first (TDD); no exceptions.

## Review Focus

- **Stale browser after relay restart:** browser reconnects to a room with no moderator; must show "Waiting for the moderator", never a stale transcript. Test: Task 2.
- **Key mismatch on browser request:** wrong or missing key on `/s/<name>/events` and vote POST → 403, no data leak. Test: Task 2.
- **Moderator reconnect with stored room:** extension re-registers the same name+key after a drop; browsers resume without rejoining (same session id). Test: Task 3.
- **Second moderator on a busy room:** relay rejects with "room busy"; first moderator unaffected. Test: Task 1/2.
- **Name conflict across browsers:** two client ids claiming "John" → second gets the conflict message; owner's last tab closing frees the name. Test: Task 5.

### Task 2: Relay service (HTTP + WSS)

**Files:** Create `relay/server.ts` (`RelayService`), `relay/page-assets.ts` note (serves the existing `page.html/css/js` from the repo root); Test `relay/server.test.ts`

**Interfaces:**
- Consumes: `RoomRegistry` (Task 1), page assets.
- Produces:
  - `class RelayService { constructor(opts?: { port?: number }); start(): Promise<void>; stop(): Promise<void>; readonly url: string }`
  - Presenter WebSocket endpoint: `GET /presenter` (upgrade) — first message must be `{"type":"register","name","key"}`; replies `{"type":"registered"}` or `{"type":"error","error":"room busy"}` then closes. Thereafter the presenter sends `{"type":"broadcast","event":<MirrorEvent or snapshot>}` and receives `{"type":"request-snapshot"}`, `{"type":"vote", ...}`, `{"type":"identify", ...}`, `{"type":"presence", clientId, connected}`; presenter replies `{"type":"reply","to":<clientId>,"body":…}` or `{"type":"broadcast","event":…}`.
  - Browser endpoints under `/s/<name>`: `GET /?key=…` (page + per-room cookie, reusing the local-mode pattern), `GET /events?key=…` (SSE; on connect the relay sends `request-snapshot` to the presenter and forwards the reply to this browser only; then all broadcasts), `POST /vote` and `POST /identify` with `?key=…` (forwarded to the presenter with the browser's clientId; the reply goes back to that browser).
  - No moderator connected: SSE sends `data: {"type":"waiting"}` and the connection stays open; on presenter attach, a snapshot is requested and forwarded.
  - Heartbeat: SSE comment `: hb\n\n` every 25 s; WS ping every 10 s, terminate if no pong within 30 s.
- [ ] **Step 1: Failing integration tests** (real server, ephemeral port, `ws` client as presenter, `fetch`/SSE as browser): register+snapshot flow reaches the browser; wrong key → 403 / presenter register rejected; second presenter → "room busy"; presenter socket close frees the room (next attach succeeds, browsers get `waiting` then a new snapshot); vote POST round-trips presenter→browser reply; heartbeat fires (use a short interval override in tests).
- [ ] **Step 2: Run — expect FAIL.**
- [ ] **Step 3: Implement `RelayService`** on `node:http` + `ws`; browser SSE clients tracked per room; `request-snapshot` fan-in with a pending-replies map keyed by clientId.
- [ ] **Step 4: Run — expect PASS. Commit** `feat(relay): relay service`.
