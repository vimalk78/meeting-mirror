# Relay v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a remote team follow a moderator's pi session through a relay on a shared host, with stable named rooms, handoff, member list and vote ticks.

**Architecture:** A transport-agnostic `Hub` in the extension owns names, presence and votes on top of the existing `MirrorState`. Two transports drive it: the existing `LocalServer` (HTTP on the laptop) and a new `RelayClient` (outbound WebSocket to the relay). The relay is a separate small Node service that only routes: browsers' SSE and POSTs on one side, the moderator's WebSocket on the other. It stores nothing beyond live connections.

**Tech Stack:** TypeScript, Node 24 (pi runtime, built-in `WebSocket` client), `node:http`, `ws` (relay server only), vitest + jsdom, npm workspaces, UBI9 Node.js 22 container, OpenShift Deployment/Service/Route.

**Spec:** `docs/superpowers/specs/2026-11-04-relay-v1-design.md`

## Global Constraints

- Room name: `/^[a-z0-9-]{3,30}$/`. Random name: 8 characters from the lowercase Crockford alphabet `0123456789abcdefghjkmnpqrstvwxyz`.
- Key: `crypto.randomUUID()`. Link: `https://<relay-host>/s/<name>?key=<key>`.
- Stored room: `pi.appendEntry("meeting-mirror-room", { name, key, relay })`; latest entry on the active branch wins.
- Env var: `MEETING_MIRROR_RELAY`. Mode per share: a link or a stored room means relay mode; otherwise the env var decides; unset means local mode.
- Local mode with a room name: notify exactly `Room names need relay mode (set MEETING_MIRROR_RELAY).`
- Confirmation prompt text: verbatim from the spec's "Confirmation prompt" section, with the room name substituted. Default answer is No.
- Name conflict message: `<name> is already in the room. Choose another name, for example <name> K.`
- Member line: `In the room: Alice ✓, Bob, John ✓ (2 of 3 voted)` while a poll is open and not revealed; otherwise `In the room: Alice, Bob, John (3)`. Ticks show voting, never the choice.
- Heartbeats: SSE comment `: ping` every 25 s (relay and LocalServer). Relay pings the moderator socket every 15 s and drops it after 30 s without a pong.
- One moderator per room. A room is freed as soon as its moderator's socket closes. No grace period.
- The relay keeps no transcript, poll, vote or room data beyond live connections. Exactly one relay replica.
- Existing protections stay: JSON content-type required on POST (415), 64 KiB body cap (413), remark capped at 500 characters, all text escaped before rendering.
- Run all tests from the repo root with `npx vitest run`; type-check with `npx tsc --noEmit` and `npx tsc --noEmit -p relay`.

## Review Focus

- **Moderator's laptop wakes before the relay noticed the dead socket.** Her reconnect sends the same key while the stale socket still holds the room. Expected: the new socket replaces the stale one, nobody sees "busy". Tests: Task 5 (relay replaces on same key), Task 6 (replaced client stops reconnecting).
- **Moderator disconnects while a join or vote is in flight.** Expected: the browser gets 503 or 504 within the request timeout, never a hanging request. Test: Task 5.
- **Many parked browsers or junk room names.** Expected: 503 above 200 connections per room or 2000 in total; empty rooms are removed. Test: Task 5.
- **A teammate presses a vote key before joining.** Expected: 401 from the hub and the join overlay appears. Tests: Task 1, Task 3.
- **Same name from a second browser after the first owner closed all tabs.** Expected: the name is handed over; the original owner rejoining while the second is present gets the conflict message. Test: Task 1.

## Rulings (decisions the spec leaves open)

- A `hello` with the **same key** as the room's current moderator replaces the old socket; the relay sends `replaced` to the old one, which stops reconnecting. A different key gets `busy`. This keeps "never takes over" for accidental new-key shares while making reconnects work.
- The page decides whether to ask for a name from the snapshot's `you` field (the hub knows each connection's client id). The session id is still created per run and sent in every snapshot.
- The per-browser client id (random, in localStorage) replaces the old per-join token.
- On the relay, `page.html`, `page.css` and `page.js` are served without a key; the key gates events, joins and votes.
- The confirmation prompt uses `ctx.ui.select(prompt, ["No", "Yes, start a new room"])` so Enter means No.
